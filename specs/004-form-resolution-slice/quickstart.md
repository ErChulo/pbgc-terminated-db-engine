# Quickstart: Form Resolution Slice

## Goal

Verify the fourth executable PBGC engine slice: deterministic
`form_resolution` on top of the existing browser-side SQLite foundation,
date-resolution slice, service-resolution slice, and compensation-resolution
slice.

## Prerequisites

- Repository is on branch `004-form-resolution-slice`.
- Existing browser app, sql.js foundation, date-resolution slice,
  service-resolution slice, and compensation-resolution slice are present.
- Existing committed v0.1.0 contracts, schemas, migrations, seeds, mappings,
  templates, and form-resolution test cases are present.

## Validation Flow

1. Start the browser app locally after implementation.
2. Confirm the existing sql.js foundation initializes from packaged static
   assets.
3. Apply or reuse the committed SQLite migrations and seeds already used by the
   prior slices.
4. Load fixture rows from `packages/tests/form_resolution_test_cases_v0.1.0.csv`.
5. For each fixture, create or select a reviewed `form_resolution` input packet.
6. Run only the `form_resolution` module.
7. Verify persisted outputs:
   - one `engine_run` row per attempt
   - one `resolved_forms_output` row per successful fixture
   - form fields populated or explicitly null according to expected fixture
     values
   - no benefit-kernel or output-adapter rows generated by this slice
   - `module_trace` rows for each populated form quantity and warning path
8. Verify expected fixture outputs for retirement type, normal single form,
   normal married form, death form, and lump-sum option.
9. Re-run the same packet five times and verify resolved values and trace
   decisions remain identical except generated identifiers and timestamps.
10. Attempt invalid packets and verify they fail before writing
    `resolved_forms_output`.
11. Run date-resolution, service-resolution, and compensation-resolution
    regression tests to confirm prior slices still pass.

## Out of Scope Checks

Do not run benefit kernel, V1/VE output, valuation listings, or BSRS
configuration in this slice.

## Completion Criteria

- Existing form-resolution fixtures pass.
- Invalid form packet checks are blocked with structured errors.
- Trace exists for every populated form output.
- Warning-bearing form paths preserve valid output values.
- Existing date-resolution, service-resolution, and compensation-resolution
  tests still pass.
- No network connection is required for deterministic execution.
- Static build output is committed when implementation changes runtime assets.
