# Quickstart: Valuation Listings Output

## Goal

Verify the seventh executable PBGC engine slice: deterministic
`valuation_listings_output` on top of the existing browser-side SQLite foundation
and the implemented date, service, compensation, form, benefit-kernel, and
V1/VE slices.

## Prerequisites

- Repository is on the active valuation-listings feature branch.
- Existing browser app, sql.js foundation, and the first six executable slices
  are present.
- Existing committed v0.1.0 contracts, schemas, migrations, seeds, official
  PBGC deliverable templates, mappings, and fixture content are present.

## Validation Flow

1. Start the browser app locally after implementation.
2. Confirm the existing sql.js foundation initializes from packaged static
   assets.
3. Apply or reuse the committed SQLite migrations and seeds already used by the
   prior slices.
4. Load the committed valuation-listings fixture set and build the reviewed
   input packet for each supported case.
5. Run only the `valuation_listings_output` module.
6. Verify persisted outputs:
   - one `engine_run` row per attempt
   - one valuation-listing output row per successful fixture
   - output fields populated or explicitly null according to expected fixture
     values
   - no BSRS configuration rows generated by this slice
   - trace records for each populated field and warning path
7. Re-run the same packet five times and verify populated values and trace
   decisions remain identical except generated identifiers and timestamps.
8. Attempt invalid packets and verify they fail before writing the authoritative
   valuation-listing row.
9. Run date-resolution, service-resolution, compensation-resolution,
   form-resolution, benefit-kernel, and V1/VE regression tests to confirm prior
   slices still pass.
10. Keep the prior-slice regression guard in place whenever valuation-listing
    validation or packet-shape rules change.

## Out of Scope Checks

Do not run BSRS configuration or other output-adapter logic in this slice.

## Completion Criteria

- Committed valuation-listings fixtures pass.
- Invalid valuation-listing packet checks are blocked with structured errors.
- Trace exists for every populated valuation-listing output field.
- Conditional branch cases preserve explicit null output values.
- Existing date-resolution, service-resolution, compensation-resolution,
  form-resolution, benefit-kernel, and V1/VE tests still pass.
- No network connection is required for deterministic execution.
- Static build output is committed when implementation changes runtime assets.
